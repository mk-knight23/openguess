# Inference at catalog scale

For current 0.2.1 behavior and measured policy comparisons, see [question quality upgrade](question-quality-upgrade.md). The sections below preserve the optimization history; their original 0.2.0 guessing gate is superseded by independent, rival-separating signature confirmation.

Question selection uses the same five-response likelihood model as v0.1. The optimization groups candidate probability into true, false, and unknown masses for each question. Mutual information is calculated as response entropy minus conditional response entropy. This is mathematically equivalent to the prior-entropy minus expected-posterior-entropy implementation, but avoids five candidate arrays and repeated posterior normalization per question.

Selection iterates the present traits of each candidate once to collect known true/false masses. Missing mass is the total candidate weight minus those two known masses. Scoring is O(present traits + questions), with O(questions) temporary aggregation space; it no longer probes every absent entity/question pair. Lexicographic question tie breaks, the 1e-10 information threshold, no repeated questions, and soft candidate evidence remain unchanged. Rankings use log weights and keep alternatives nonzero. Null and omitted facts share an uncertain response model; an unknown user answer contributes no evidence.

The confidence value is conditional on the loaded catalog and model, not a calibrated real-world accuracy claim. Missing facts do not become false facts. Incomplete profiles can still accumulate model-relative evidence from other traits, so exhausted questions should lead to an uncertain result or contribution flow. Identical signatures cannot be distinguished by questioning; the existing 85% threshold does not auto-guess such uniform ties. Explicit rejection can leave one candidate, which is an exclusion result rather than proof of identity.

## Verification

Focused tests cover normalization, contradictions, unknown/missing facts, deterministic ties, question exhaustion, recovery, and equivalence to an independent naive posterior-entropy reference across twelve sparse weighted fixtures. A synthetic benchmark covers 2,500 entities with 150 questions and 20% unknown facts. On Node 24.19.0 on the development Mac, the initial aggregated selection took 19.6 ms (before the later sparse-trait optimization). The test uses a generous 1,000 ms ceiling to catch regressions without claiming a universal device speed. Existing baseline tests passed before the optimization; the aggregation preserves raw information-gain calculations. The later semantic policy changes which question is selected, as described below.

No persistent per-entity indexes, backend service, network requests, or paid APIs are required by this engine. Inference already uses a worker; column-oriented traits may reduce CPU costs if browser measurements justify that complexity.

## Responsive inference worker

Larger packs can include thousands of questions. `useInference` hydrates one module worker per loaded pack, then sends only answer history, exclusions, and a monotonically increasing request ID. Results contain IDs and probabilities; the hook resolves IDs against the original pack rather than cloning character profiles on each answer. New packs terminate the old worker, and late results from previous workers or requests are ignored. The hook reports `busy` and a readable error so the UI can pause answer controls while computing. Browsers without Worker support use synchronous inference; this compatibility fallback can temporarily block on large packs. Worker startup and runtime errors are surfaced rather than silently retrying expensive work on the UI thread.

The sparse-pack complexity regression uses 1,100 profiles with 35 present facts and 2,037 questions. The earlier implementation read 2,240,700 traits; the sparse implementation reads 38,500. This deterministic operation-count check avoids a timing threshold tied to a particular device. Independent naive entropy fixtures cover null/missing facts and weighted candidates; additional tests cover zero-weight members, unrelated traits, and exhausted known evidence. Actual pack timings are reported in `benchmarks.md`.

## Meaningful semantic clues

Name-letter, spelling, name-length, and direct name-property clues are excluded at the engine boundary, including legacy pack IDs and unmarked orthography wording. The data importer also removes these traits and questions. Meaningful questions about a namesake or inventor remain allowed.

Each eligible question keeps its raw expected information gain for explanations. Selection priority multiplies that gain by the square root of the currently known true/false probability mass. This favors broad, documented semantic splits over rare claims surrounded by unknown profiles. Reusing the immediately preceding semantic family has a modest 10% score cost. A clearly better question can still win within the same family; diversity never creates information or random unrelated questions. Ties remain deterministic. These are transparent design heuristics, not another game's private algorithm.

Confidence gating still requires at least three informative answers and an 85% catalog-relative top weight, except when only one non-rejected candidate remains. Reaching the question budget or exhausting meaningful facts does not turn a weak best match into a confident identity. The semantic evaluation reports those rounds as unresolved. Tests cover legacy and unmarked spelling exclusion, coverage preference, useful family variation, stronger same-family evidence, actual pack turns, and absent/null/zero-weight facts.

Rounds may supply an optional numeric seed. The engine varies only among semantic questions whose selection score lies within 5% of the best current score. A reproducible hash of the seed, answer history, and question ID chooses among those near-equal options. Stronger information or coverage wins over arbitrary variety. The default seed zero preserves deterministic legacy behavior. Replaying the same seed and evidence—including Undo—returns the same question; a fresh round can choose a different equally useful clue. The worker and hook carry the seed as part of their input identity so a previous round's result cannot enable stale controls.
